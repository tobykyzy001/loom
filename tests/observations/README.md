# Source-bound MemoryObservation and manual review test

This directory verifies a **narrow project-scoped MemoryCandidate lifecycle**, not automatic transcript listening, model-generated habits, or a general M5 runtime.

Run:

```sh
node tests/observations/candidates.mjs
node tests/observations/candidates.mjs --browser
cargo test -p loom-concierge observation -- --test-threads=1
cargo test -p loom-concierge memory_candidate_edit --locked -- --test-threads=1
```

The driver creates isolated projects and a real signed outbound Node registration, mappings and explicitly authorized read_summary Ticket references. It then uses the controller's normal authenticated `POST /api/v1/candidates` for **manual source selection**. A Source Ticket being real does not mean that its associated task completed. There is no assumption that manually submitting three references means a model recognized a preference.

## Proven contractual bounds

- Every observation requires the known real project, a supported kind, and one to 32 unique bounded source Ticket IDs. All source Tickets must actually be registered to the same project. Repeated references or repeated submission of the same Ticket do not inflate the observation count.
- A Memory projection (`loom.memory-candidate.v1` in its content) requires its explicit source refs. A source/count history is merged rather than replaced. After its recorded expiry, a subsequent fresh source begins a new bounded count; existing candidate history remains readable but the response does not call that another promotion. This is not a durable global learning claim.
- A separate, separately verified Skill candidate remains possible from a selected valid source before it runs the normal single deterministic `read_summary` replay. Without that real replay and distinct immutable Artifact SHA match, accepting it still fails. `tests/skills/read-replay.mjs` preserves the full original source→independent replay proof. A single or repeated Skill-observation POST is not execution by itself.
- A Memory review may only create one derived project Memory after a pending/postponed explicit accept. It attaches all source refs to a precise immutable `candidate_memory_links` relationship and attaches the earliest Ticket to the Memory. The schema tag is not a Grant or a learned-quality score.
- `never` is a distinct, reversible no-repeat suggestion status. `later` allows a later explicit review. An accepted Memory may not be silently rewritten by a later review decision; a repeated accept creates no second Memory. `route` cannot be accepted as a Memory, and an unknown kind cannot fall through an untyped `else` branch.
- Candidate undo and ordinary `DELETE /memories/{id}` use the **same exact-link transaction** for a linked Memory: delete its child link, then its exactly identified derived Memory, and return the candidate to pending, all-or-nothing. No observation history, Ticket, Artifact, Grant or working task is rolled back. An accepted legacy candidate without an exact link is read-only history through this special action; other unrelated Memory rows are not searched/deleted.
- The Memory edit endpoint honors explicit supported scope changes/known project IDs rather than silently discarding them. A linked Memory changed by direct manual editor keeps its original precise candidate link; the undo link targets only that unique derived Memory. This is not a cross-project evidence-transfer mechanism.
- **A source-bound pending/postponed MemoryCandidate has its own explicit text-correction action** (`decision:"edit", content, expected_version` on the existing candidate PATCH). Only those exact three body fields are accepted, with the actual current JSON integer version. The preference text is nonempty, at most 500 UTF-8 bytes and has the same bounded credential/resource-locator exclusions as candidate acceptance. Extra scope/project/source fields, other candidate kinds, terminal history, malformed v1 projection or missing existing sources cannot acquire new meaning through this action.
- That edit preserves the candidate ID, status, original project / scope, schema, `repeated_explicit_choices` source and **original raw-observation fingerprint**, changing only proposal content and advancing version by one. It is *not* acceptance or an observation. Identical text at the current version is a no-op with no version/audit; an older version, even with identical-looking text, returns 409 `candidate_version_conflict`. `BEGIN IMMEDIATE`, guarded UPDATE and one `candidate.memory.edited` audit commit together or restore the original record. Audit has real source/version metadata and no before/after preference text. A later separate accept is still required to derive a Memory and its exact link.
- The regression freezes the **raw value before any edit**. Re-observing that value plus a new real same-project Ticket increments the matching observation from three to four, adds the precise new source there in first-seen order, and returns the original candidate with its edited text and unchanged fingerprint/version. It does not treat the edited proposal as if it were the raw value; nor does it silently append that new source to the existing candidate's own source_refs / old accepted link. The raw observation group is not a semantic-equality algorithm or execution authority.
- In actual Edge, cancelling a draft produces no PATCH. Saving a correction is different from saving a Memory: backend version/fingerprint/sources are checked while the visible Memory list remains empty. It then separately accepts through the existing confirmation action. A dedicated `GET /candidates` 503 after a real successful edit leaves the correction textarea and error visible until an ordinary reload recovers the genuine latest candidate; a second retained 503 case proves the older accept/confirmation boundary too. The narrow 390px check opens the real editor, bounds its actual box and cancels without another write.
- If the user edits the derived Memory and then explicitly deletes that **currently edited** record, the latest loaded Memory list no longer contains its ID. The ordinary editor is reset rather than continuing to display the removed Memory's content/scope after a later independent accept creates a different ID. It remains independent of the candidate editor and no second memory mutation/audit is fabricated by clearing the form.

- An optional direct Memory `source_ticket_id` must point to an actual Ticket. When `project_id` is also given (including ordinary `scope=project`), it must be the same project as that Ticket; a cross-project referenced origin cannot be persisted or entered under that Ticket's audit trail. An absent source remains allowed for a freely chosen user preference and a nontext source ID is rejected rather than discarded. Source equality does not imply the previous Ticket succeeded, grant access to it, or prove a learned habit. Positive controls retain a same-project origin and a standalone no-source Memory, and rejection produces no Memory write or corresponding creation audit (the checked action list is unchanged). Candidate acceptance still chooses only its already verified immutable refs; ordinary edits neither invent nor transfer the candidate's historical source.

## Browser-only evidence

The `--browser` option opens a new **isolated Edge** context only against the local Vue+Rust fixture, authenticates with that fixture's client token and actually confirms both save and withdrawal in the existing ConfirmationDialog. It verifies exact PATCH decision bodies, the server-derived-link UI, **direct reload on the Memories page**, no leaked token in screenshots and a 390px viewport. It also explicitly edits an accepted candidate's Memory through the real form from project to user scope: the request adds no new `source_ticket_id`, the original source remains fixed, and the candidate remains accepted against the same linked Memory. Deleting that Memory through the actual delete dialog atomically returns the same candidate to pending; a new accept then uses a different derived Memory ID and the still-valid original sources. Manual correction is not reclassified as a fresh observation or a new execution grant. It deliberately returns the pending state without making any new Grant/Ticket or running a model/worker. The local browser profile's local storage is cleared and its owned temporary profile is removed on exit. The narrow viewport is not a physical iOS/Android certificate.

- Ordinary explicit edits have `memory.explicit_updated` with real Memory ID, old/new scope, version transition, content/project change flags and the immutable original source relation; the `audits.ticket_id` is not injected from the edit request. Ordinary unlinked deletes have `memory.explicit_deleted` with original scope and `candidate_withdrawal:false`. Candidate-linked deletion instead has only its established candidate withdrawal, never a duplicated general delete fact. Audit metadata does not copy the preference body or a secret.
- `cargo test -p loom-concierge explicit_memory_creation_and_audit_fail_together -- --nocapture` closes the corresponding **creation** gap: previously a valid direct Memory write could survive if its `memory.explicit_saved` audit subsequently failed. The real authenticated Router POST now encloses Memory INSERT and that audit in one `BEGIN IMMEDIATE`. The accepted SQL trigger specifically rejects only this saving audit and proves the response still follows the existing audit-error mapping (400 `invalid_request` here). The fixture's row and complete real Project record are then inspected: Memory=0, saving audits=0, the Project is unchanged and Grants=0. No worker/model execution or grant follows from this correction. Schema16 and Source/scope/response semantics remain. This is a synchronous creation-rollback proof.

The **same complete real HTTP driver** additionally injects `owned_creation_audit_failure` before one valid same-project direct Memory creation, rejects the audit, removes that exact owned trigger and then creates **the same valid input through the same live Concierge and the ordinary client**. It verifies unchanged base Memory/audits after rejection, then the actual recovered Memory version/scope/project/original source and one matching `memory.explicit_saved`. A normal public DELETE removes only that newly created record; its own deletion keeps `authority_changed:false` and `candidate_withdrawal:false`. The whole pre-existing Grants collection must remain deeply equal, not merely keep its old count. The later candidate/full Edge workflow and controller reopen still pass, with triggers and extra Memory removed. This proves the bounded same-center creation and recovery, not generic multi-host, arbitrary failure mode or learned preference semantics. An in-process probe's extension once parked at `client -> State.lock`; that observed thread context alone must not be generalized into a production network-lifecycle claim in contradiction with this real driver.

- Each UPDATE/unlinked DELETE and its matching audit share an explicit existing Store transaction. The edit rereads the actual row after the mutation and verifies version/time/project/source relationships before commit. In the real fixture, a SQL trigger rejects audit insertion for each of the two action names: the corresponding HTTP response is 500, the Memory's original content/scope/version/time/project/source and complete pre-existing audit list remain unchanged; the failed operation is not retroactively claimed. Removing the trigger then allows one real edit and delete, and the ordinary event JSON survives the real Concierge reopen. Missing IDs still return 404 without fabricated successful-operation audits.

## Scope identity is not inferred from a project association

`Memory.scope` rather than `project_id` determines the displayed and editable scope. An explicit user preference may legitimately retain a project association; a plain `user -> user` edit must **not** remove that relation. The backend preserves association on an unchanged scope, while an explicit `project -> user` conversion continues to clear it as before, and `user -> project` uses the actual explicitly selected existing project. A different valid project ID is accepted only when real; an unknown requested project returns 404 and preserves the prior row and audits. `cargo test -p loom-concierge user_scope_edit_preserves_project_relation_but_scope_change_is_explicit -- --nocapture` verifies those HTTP/store changes, two ordinary update audits and no Grant creation.

The UI now opens only its supported `user`/`project` editor with the actual current scope. `worker` and `host` preference cards display their original scope and keep ordinary viewing/deletion available, **but cannot enter a user/project form that would silently turn them into `scope=user`**. That is an editor capability boundary, not globally disabling any related server API or pretending a Host cannot run. Unknown scopes stay visibly scoped/read-only. A `user+project_id` card also corrects the earlier "user means no project relation" misconception. Scope data is not a new authorization mechanism.

The full Edge case `node tests/observations/candidates.mjs --browser` still exercises the original candidate lifecycle and source-preserving UI edits, then appends real worker, host and associated-user preferences. Host/worker edit buttons are disabled and produce no scope-change request or edit audit; associated-user editing first preserves its existing project_id and later explicitly chooses **another real project**. The latter is a real owned, registered directory/project with no new Grant, not a synthetic label or first-list-row implied choice. The 390px labels and body fit, the extra records are removed, grants stay unchanged and the main later withdrawal leaves zero Memory. This tests a bounded user-controlled edit, not a generic semantic classifier, cross-project Ticket re-attribution or mobile/actual-DSH environment.

## Exact migration and database validity

Schema 11 additively creates `candidate_memory_links`. It does not change the independent Skill replay protocol or previously stored model records. Existing `v6` migration tests preserve original Ticket/Artifact/Grant/audit facts. The full raw migration also retains older Model provenance, and v3/v7/v8/v9/v10→11 unit tests check that history can still be opened. Unknown later versions are still refused. **Current default Store is schema15**: schema12/13 add Source intake/threads and immutable source↔explicit-task mapping; schema14 separately stores sanitized code-evidence projection. Schema15 additively preserves that history and adds bounded integer `tickets.priority` with default 0, for authorized ordinary scheduling—not new Grant, task operation or learned-preference authority. This driver expects `user_version=15` and repeats the real reopen against that version; the separate storage future-version guard rejects versions greater than 15 and unknown later schemas are not read. No down-version migration is made inside this test for convenience.

The initial prototype's repeated SQL UPDATE was diagnosed with a minimal Store transaction test, not ignored. Under the current rusqlite binding/version, the numbered-placeholder update returned zero affected rows even though the equivalent row predicate found exactly one record. Explicit named SQL bindings have concrete DB/read-back evidence that both occurrence count and exact source union persist. No claim is made that this validates a different rusqlite release.

No real user/private transcript, production DSH Profile, OS credential provider, guild/team identity, arbitrary source-directory operation, new worker execution or remote/TLS experience is tested by this script. Its temp projects are explicit synthetic fixtures. Python only reads/adjusts that one owned SQLite fixture for the expiry scenario and simple integer reads; it does not grant permissions or interface with another provider. The HTTP driver always creates its own node identity and mappings, and tests no new authority is created.

## Review defects found and fixed

The first refactoring had to preserve the old legacy Memory fixture with no source tag (`source_refs:[]`) but cannot allow a new v1 source-bound projection to opt into that exception. Invalid/missing arrays, duplicate or object refs, and unsupported schema metadata are not shown as legacy evidence. Old accepted candidates without an exact association remain historical/read-only rather than arbitrarily guessed into an undo.

Independent review also identified the FK failure from the pre-existing direct Memory delete, missing candidate loading on direct Memories-page reload, and the old resource loader returning `undefined` despite all successful reads. All three have regression coverage. A mutation confirmation now requires a successful resource refresh to close; if the write has been accepted but the next read fails, the UI exposes that separate condition and leaves the stale state explicit.

Subsequent strict-state tests assert accepted is undo-only, never cannot become later/rejected, rejected cannot become later/undo/accept, and identical never/rejected decisions do not change audit/version. Presence of `schema:null`, a number/boolean/unknown schema, or new v1 without refs is not a legacy waiver. The controller also denies them, rather than depending solely on the frontend. An old accepted candidate without an exact link cannot silently delete an unrelated Memory; one unrelated manual Memory is retained when the linked record is withdrawn and can only be removed by its own ordinary deletion.

The browser now additionally performs later, never → explicit restore (the button no longer incorrectly implies saved-preference deletion), and rejection of a separate legitimate source-bound candidate with only a read-only rejected-history presentation. Repeated rejection/version and later-after-rejected refusal are verified from the controller. A deliberately injected single `GET /candidates` HTTP 503 after a real accepted PATCH leaves an explicit visible “accepted but not refreshed” confirmation. Returning to inspecting, refreshing again, then undo restores pending without duplicate Memory/authority. This is the bounded UI read-failure path, not an arbitrary provider outage or checkpoint of remote distributed updates.

The original weak negative setup created an undefined ticket reference before creating the actual ticket, which could mask every input-specific rejection. The setup was corrected to create registered Ticket references first and assert their concrete refusal reasons before any successful memory/candidate write. Default HTTP has three generated Memory/route candidates; browser adds a separate valid rejected-history candidate. Seven focused Vue tests exercise state/provenance decisions plus the source/version/fingerprint guard for offering edit, rather than relying on a few selected buttons.

This file documents the bounded evidence and failure gates only. Full editing of projects/users' preference scope, actual automatic HabitObservations, semantic summarization, automatic workflow induction, conflict resolution, batch history review, general route candidates, company/personal isolation, and speculative execution remain future milestones or explicitly NOT RUN.
